# Sub-proyecto 2: Infraestructura de Agentes — Spec

## Contexto

Sub-proyecto 2 de la secuencia definida en `2026-09-01-separacion-y-nivelacion-antigravity-nano.md`. El Sub-proyecto 1 (repo base, `pyproject.toml`, entorno conda `sys_agents`, CI) ya está completo y publicado. Este sub-proyecto construye los 8 agentes de software con `SKILL_METADATA` en `src/multiagent_core/`, réplica del patrón ya probado y calificado 98/100 en Programming-Logic-Agentic-AI-Development (LP) y Probability-Statistics-Agentic-AI-Core (Probabilidad), más 3 componentes de soporte sin esa convención de agente pero igual de necesarios para que los 8 funcionen de verdad: `MermaidNodeCounter` (`_mermaid_utils.py`), `MermaidRenderer`, y `pdf_indexer.py` (ver "Hallazgos de revisión" abajo — el orden de construcción de la sección correspondiente lista los 11 componentes en total).

## Hallazgos de revisión (agregado tras relectura contra el código real de LP)

Una relectura de las interfaces reales de `src/multiagent_core/` en LP (no solo de su documentación) encontró 7 desajustes entre la primera versión de esta spec y el patrón que realmente rige los repos ya calificados 98/100 — corregidos abajo antes de pasar a `writing-plans`:

1. **`SKILL_METADATA`**: cada agente de LP declara un diccionario a nivel de módulo (`name`, `description`, `version`, `input`, `output`, `requires_api_key`) inmediatamente después de los imports — es la forma en que `OrchestratorAgent` y herramientas externas (o futuros LLMs que orquesten agentes) descubren la interfaz de cada agente sin leer su código. Ausente de la primera versión de esta spec; se adopta como convención obligatoria para los 8 agentes de este repo.
2. **`OrchestratorAgent.run(...)` no es el método real** — en LP es `generate_pedagogical_report(student_code: str, unit_number: int, test_file_path: Path | None = None) -> str`, con routing automático por tipo de entrada (`_detect_input_type`: pseudocódigo / Python con funciones / Python sin funciones vía `ast.parse` + detección de palabras clave) que decide qué sub-agentes invocar — pseudocódigo omite auditoría de estilo/seguridad y usa `PseudocodeAgent` para el diagrama en vez de `FlowchartAgent`. `PseudocodeAgent` faltaba en la lista de dependencias de `OrchestratorAgent` en la primera versión. Corregido en la sección de Interfaces abajo.
3. **Nombres de método reales de `CodeAuditorAgent` y `EvaluatorAgent`**: `CodeAuditorAgent` tiene además `generate_report(student_code: str, test_file_path: Path | None) -> str` (consolida `audit_style`+`audit_security`+`run_pytest` en un reporte Markdown — es lo que `OrchestratorAgent` invoca, no los 3 métodos por separado). `EvaluatorAgent.evaluate(student_code: str, test_file_path: Path | None) -> dict` es el nombre real (no `evaluar`, que tenía la primera versión de esta spec), y su dict de retorno incluye la clave `retroalimentacion` (texto Markdown ya formateado) además de los criterios individuales.
4. **Patrón de mocking para tests de `TutorAgent`**: LP mockea `patch("...tutor_agent.genai.Client")` + `monkeypatch.setenv("GEMINI_API_KEY", "key-de-prueba")` — nunca llama a la API real de Gemini en tests unitarios. Se fija como el patrón obligatorio aquí también (la sección de Estándar de Calidad de la primera versión decía "se mockea" en general, sin el patrón concreto).
5. **Faltaban dos componentes de soporte sin los cuales `NotebookCompilerAgent`/`FlowchartAgent`/`PseudocodeAgent` no funcionan de verdad**: `MermaidRenderer` (`mermaid_renderer.py`) convierte texto Mermaid a SVG estático con caché por hash de contenido, vía `npx @mermaid-js/mermaid-cli` (mismo prerequisito de Node.js ya documentado en el `CLAUDE.md` de LP) — es la dependencia inyectada en `NotebookCompilerAgent.__init__` **y también en `ContentAuditorAgent.__init__`** (LP lo inyecta en ambos), no un detalle opcional. `_mermaid_utils.py` (`MermaidNodeCounter`) es la utilidad compartida de generación de IDs de nodo (`node_1`, `node_2`, ...) entre `FlowchartAgent` y `PseudocodeAgent`. Ambos se agregan al orden de construcción y a las interfaces abajo. Tests de `MermaidRenderer` mockean `subprocess.run` y `shutil.which` (patrón confirmado en `tests/test_mermaid_renderer.py` de LP) — nunca invocan `npx` real, así que el CI de este repo (que no instala Node.js, igual que el de LP) no lo necesita para que la suite pase.
6. **`pyproject.toml` del Sub-proyecto 1 no declara ninguna de las dependencias externas reales que estos agentes necesitan**: solo tiene `numpy` y `python-dotenv`. Inspección de los imports reales de LP confirma que hacen falta `chromadb`, `sentence-transformers` (vía `SentenceTransformerEmbeddingFunction`), `google-genai`, `nbformat` (para `NotebookCompilerAgent`), y `pypdf` (para indexar bibliografía en PDF, parte del alcance de `TutorAgent`). Se agrega como primera tarea técnica de este sub-proyecto: actualizar `[project.dependencies]`/`[project.optional-dependencies]` de `pyproject.toml` y `environment.yml`, verificando `pip install -e ".[dev]"` dentro de `sys_agents` antes de escribir el primer agente — mismo principio que ya evitó el riesgo de packaging roto en el Sub-proyecto 1.
7. **`pdf_indexer.py` de LP es un módulo de funciones puras, no una clase** (`extract_pages(pdf_path: Path) -> list[str]`, `chunk_page_text(...)`, `index_pdf(pdf_path: Path, max_chars: int = ...) -> list[dict]`), importado directo por `TutorAgent` (`from .pdf_indexer import index_pdf`) para construir el índice de bibliografía en `_build_bibliografia_index()`. Es un prerequisito de `TutorAgent`, no un detalle interno de su clase — se agrega como componente propio en el orden de construcción, con su propio ciclo TDD, antes de `TutorAgent`.

## Decisiones de diseño (brainstorming, confirmadas por el usuario)

1. **`SafetyGateAgent` es genérico en este repo, no específico de nanotecnología/química.** La spec original de separación decía "idénticos en ambos repos" para los 8 agentes, pero eso contradecía la razón de ser de la separación: `stability_guardian.py`/RDKit son herramientas de química, exactamente lo que este repo debe NO tener. Resolución: aquí `SafetyGateAgent` valida guardrails genéricos de outputs de agentes (prompt injection reflejado, formato esperado, filtrado de secretos) y reconecta la idea de retroalimentación socrática de forma genérica. En Antigravity-Nano (Sub-proyecto 4), se extiende con las validaciones químicas reales (RDKit, `stability_guardian` rescatado) — mismo nombre de clase, responsabilidad base compartida, especialización distinta por repo.
2. **8 agentes heurísticos salvo `TutorAgent`, que usa LLM (Gemini).** Se evaluó explícitamente la alternativa de dar LLM a más agentes ("sistemas multiagente de verdad") y se descartó: los 7 agentes de auditoría/compilación/evaluación necesitan ser deterministas y verificables para servir como gate de calidad — un auditor de seguridad no determinista es un auditor roto. "Sistemas multiagente reales" (LangGraph/CrewAI/ADK, LLMs orquestando LLMs) es tema de **contenido pedagógico** del Sub-proyecto 3 (lo que el curso enseña a construir), no un cambio de arquitectura de estos 8 agentes de tooling.
3. **`TutorAgent` se construye ahora, sin contenido pedagógico real todavía.** El Sub-proyecto 3 llena `lecciones/` y `bibliografia/` con contenido real; este sub-proyecto construye el agente completo (RAG con ChromaDB + Gemini) probado con TDD sobre una carpeta `lecciones/` mínima/de prueba. El código del agente no cambia cuando el contenido real llegue.
4. **`TutorAgent` usa Gemini** (`google.genai`, `GEMINI_API_KEY`), mismo patrón que LP/Probabilidad — no un proveedor distinto.
5. **`ContentAuditorAgent` usa un set de 6 dimensiones propio de este repo** (no las 5 de LP ni las 9 de Probabilidad, aunque el patrón general — heurístico, sin LLM, reutiliza `CodeAuditorAgent` — sí se hereda):
   1. LaTeX bien formado (matemáticas de ML/optimización).
   2. Patrón pedagógico propio completo (Hilo de Oro / Ciclo de Verificación Triple / equivalente — su nombre se define en el Sub-proyecto 3; esta dimensión audita que el ciclo esté citado y completo, sea cual sea su nombre final).
   3. Código de ejemplo con docstrings, type hints, sin riesgos OWASP.
   4. Reproducibilidad de agentes: seeds fijados, configuración explícita de modelo/temperatura en cualquier ejemplo con LLM, ninguna clave de API hardcodeada.
   5. Diccionario de Variables verificado contra código realmente ejecutado en la propia unidad (mismo criterio estricto que causó rechazos reales de revisión en Probabilidad: nunca un símbolo listado que solo aparece en una tabla genérica o docstring en prosa).
   6. Invariantes estructurales: fences de código balanceados, celdas de autoevaluación consistentes.

## Arquitectura

Mismo patrón exacto que LP: cada agente es una clase en su propio archivo bajo `src/multiagent_core/`, sin LLM salvo `TutorAgent`, rutas de archivo/directorio siempre inyectables en el constructor (nunca hardcodeadas) para poder aislar tests con `tmp_path`. Las utilidades reales rescatables de `external_skills/` de Antigravity-Nano (`context_loader.py`, `github_skill_loader.py`, `token_budget_guard.py`, `output_scorer.py`, `episodic_retriever.py`, `graph_memory.py`, `basis_set_architect.py`, `stability_guardian.py`, `trace_annotator.py`, `task_classifier.py`) se copian a este repo bajo `src/multiagent_core/_vendored/` si el agente que las necesita ya está en el orden de construcción de este sub-proyecto; si ninguno las necesita todavía, su copia se pospone al sub-proyecto de contenido/migración que sí las use — evita importar código sin un consumidor real (YAGNI).

## Orden de construcción (cada tarea depende de la anterior salvo que se indique independiente)

1. `_mermaid_utils.py` (`MermaidNodeCounter`) — independiente, utilidad compartida.
2. `FlowchartAgent` — depende de `MermaidNodeCounter`.
3. `PseudocodeAgent` — depende de `MermaidNodeCounter`.
4. `CodeAuditorAgent` — independiente.
5. `ContentAuditorAgent` — depende de `CodeAuditorAgent`.
6. `MermaidRenderer` — independiente (requiere `npx @mermaid-js/mermaid-cli`, prerequisito de Node.js ya usado en LP).
7. `NotebookCompilerAgent` (+ `MathAgent` interno) — depende de `FlowchartAgent` y `MermaidRenderer`.
8. `EvaluatorAgent` — depende de `CodeAuditorAgent`.
9. `SafetyGateAgent` — independiente.
10. `OrchestratorAgent` — depende de `CodeAuditorAgent`, `FlowchartAgent`, `PseudocodeAgent`, `EvaluatorAgent`, `SafetyGateAgent`.
11. `pdf_indexer.py` (funciones puras: `extract_pages`, `chunk_page_text`, `index_pdf`) — independiente.
12. `TutorAgent` — depende de `pdf_indexer.py`, ChromaDB, Gemini.

## Interfaces (contratos exactos — el plan de implementación no debe inventar firmas nuevas)

Todas las clases en `src/multiagent_core/<snake_case>.py`, imports absolutos desde raíz (`from src.multiagent_core.<agente> import <Clase>`). Cada módulo declara `SKILL_METADATA` a nivel de módulo (`name`, `description`, `version`, `input`, `output`, `requires_api_key`) inmediatamente después de los imports, igual que en LP.

- **`MermaidNodeCounter`** (`_mermaid_utils.py`, sin `SKILL_METADATA` por ser utilidad interna, no un agente): `__init__() -> None`; `next_id() -> str` (retorna `"node_N"`, N inicia en 1). Compartida por `FlowchartAgent` y `PseudocodeAgent`.
- **`MermaidRenderer`**: `__init__(output_dir: Path) -> None`; `render(mermaid_source: str) -> Path` (confirmado idéntico a la firma real de LP; retorna la ruta del `.svg` generado o cacheado por hash SHA-256 del contenido, vía `npx @mermaid-js/mermaid-cli`).
- **`FlowchartAgent`**: `__init__() -> None`; `build_mermaid_flowchart(code_source: str) -> str`.
- **`PseudocodeAgent`**: `__init__() -> None`; `pseudocode_to_mermaid(pseudocode: str) -> str`; `python_to_pseudocode(code_source: str) -> str`; `pseudocode_to_python_skeleton(pseudocode: str) -> str`.
- **`CodeAuditorAgent`**: `__init__() -> None`; `audit_style(code: str) -> list[str]`; `audit_security(code: str) -> list[str]`; `run_pytest(test_file_path: Path) -> dict[str, Any]`; `generate_report(student_code: str, test_file_path: Path | None = None) -> str` (consolida los tres anteriores en un reporte Markdown — es el método que `OrchestratorAgent` invoca).
- **`ContentAuditorAgent`**: `__init__(mermaid_renderer: MermaidRenderer | None = None) -> None` (inyectable, igual que en LP; sin `programa_path` — este repo no tiene la dimensión de "alineación curricular contra programa oficial" de LP, ver decisión de las 6 dimensiones arriba); `audit_unit(md_path: Path) -> dict[str, Any]` — retorna hallazgos por cada una de las 6 dimensiones fijadas arriba, más un resumen (`passed: bool`, `score: float` o estructura equivalente, a definir en el plan siguiendo el estilo de retorno de LP).
- **`NotebookCompilerAgent`**: `__init__(mermaid_renderer: MermaidRenderer | None = None, asset_base_url: str = ...) -> None`; `compile(md_filepath: Path, output_dir: Path) -> Path`. `MathAgent` como clase interna del mismo archivo (`process_latex(text: str) -> str`), igual que en LP.
- **`EvaluatorAgent`**: `__init__() -> None`; `evaluate(student_code: str, test_file_path: Path | None = None) -> dict[str, Any]` (nombre real de LP, no `evaluar`) contra **5 criterios** (corregido: la primera versión de esta spec decía 4, pero el código real de LP tiene 5 — "Corrección lógica", "Proceso (Hilo de Oro / equivalente)", "Calidad de código", "Pruebas (pytest)", "Reproducibilidad") de una rúbrica genérica propia de este repo. El dict de retorno sigue el formato real de LP: `{"criterios": {...5 entradas, cada una con "nivel" y "retroalimentacion"...}, "calificacion_final": float (0-100, promedio de los 5), "retroalimentacion": str (resumen Markdown consolidado)}`. El contenido exacto de la rúbrica (nombres finales, descripciones por nivel) se redacta en el Sub-proyecto 3; esta tarea construye el motor de evaluación con los 5 criterios y su mecánica de puntaje, con niveles/descripciones placeholder testeables.
- **`SafetyGateAgent`** (nuevo): `__init__() -> None`; `check_output(agent_output: str) -> dict[str, Any]` — retorna hallazgos de guardrails genéricos: patrones de prompt injection reflejados en el output, ausencia de secretos/claves filtradas, formato esperado no violado.
- **`OrchestratorAgent`**: `__init__() -> None` (instancia `CodeAuditorAgent`, `FlowchartAgent`, `PseudocodeAgent`, `EvaluatorAgent`, `SafetyGateAgent`); `generate_pedagogical_report(student_code: str, unit_number: int, test_file_path: Path | None = None) -> str` (nombre real de LP, no `run`) — reporte Markdown único. Incluye `_detect_input_type(student_code: str) -> str` (routing automático vía `ast.parse` + detección de palabras clave del pseudocódigo del repo, igual mecanismo que LP): pseudocódigo omite auditoría de estilo/seguridad y usa `PseudocodeAgent.pseudocode_to_mermaid` para el diagrama; Python con funciones usa `FlowchartAgent`; Python sin funciones omite el diagrama. `SafetyGateAgent.check_output` se aplica sobre el reporte final antes de devolverlo. `ContentAuditorAgent` se invoca aparte cuando se provee `md_path` (no es parámetro de `generate_pedagogical_report` en LP; este repo puede exponerlo como parámetro opcional adicional si el plan lo justifica, documentándolo explícitamente como una divergencia intencional del patrón LP).
- **`pdf_indexer.py`** (módulo de funciones puras, sin clase, sin `SKILL_METADATA`): `extract_pages(pdf_path: Path) -> list[str]`; `chunk_page_text(text: str, page_number: int, max_chars: int = DEFAULT_MAX_CHARS) -> list[dict]` (trocea respetando límites de párrafo, retorna `[{"text": str, "page": int}, ...]`); `index_pdf(pdf_path: Path, max_chars: int = DEFAULT_MAX_CHARS) -> list[dict]`. Consumido por `TutorAgent._build_bibliografia_index()`.
- **`TutorAgent`**: `__init__(course_dir: Path, chroma_path: Path | None = None, memory_path: Path | None = None, bibliografia_dir: Path | None = None) -> None` — construye el índice ChromaDB de forma eager en el constructor (`_build_index()`), mismo patrón que LP; `ask(question: str) -> str` — crea el `Client` de Gemini de forma perezosa dentro de este método, leyendo `GEMINI_API_KEY` de `os.environ` en ese momento (nunca en `__init__` ni a nivel de módulo), para que el agente sea instanciable sin la key (solo `ask()` retorna un mensaje de error controlado). Tests unitarios mockean `patch("...tutor_agent.genai.Client")` + `monkeypatch.setenv("GEMINI_API_KEY", "key-de-prueba")` — nunca llaman a la API real de Gemini. Sin integración a Materials Project (eso es específico de Antigravity-Nano) ni a bibliografía de nanotecnología — la carpeta `bibliografia_dir` es genérica para PDFs de IA/ML/Sistemas Multi-Agente.

## Estándar de calidad

- TDD estricto para los 8 agentes y los 3 componentes de soporte, sin excepción — test que falla primero, luego implementación mínima, sin importar si el componente envuelve una utilidad rescatada o no.
- `ruff check` limpio en cada commit y en CI (ya configurado en Sub-proyecto 1).
- Rutas de archivo/directorio siempre inyectables en constructores — nunca hardcodeadas — para aislar tests con `tmp_path`, igual que TutorAgent de LP.
- Ningún agente hace red real en sus tests (Gemini, cualquier API externa se mockea en tests unitarios con el patrón fijado arriba para `TutorAgent`; una prueba de integración real con Gemini, si se incluye, se marca explícitamente y no corre en CI sin `GEMINI_API_KEY`).

## Fuera de alcance de este sub-proyecto

- Contenido pedagógico real (`lecciones/*.md`) — Sub-proyecto 3.
- Nombre final del patrón pedagógico central (Hilo de Oro / equivalente propio) — Sub-proyecto 3.
- Redacción final de la rúbrica de 5 criterios de `EvaluatorAgent` (nombres definitivos, descripciones por nivel) — Sub-proyecto 3 (aquí se construye el motor con los 5 criterios y niveles/descripciones placeholder testeables).
- Migración/adaptación de estos agentes a Antigravity-Nano, incluyendo la especialización química de `SafetyGateAgent` — Sub-proyecto 4.
- Integración con Materials Project API — específica de Antigravity-Nano, no de este repo.
